1. 选择部署方式

适用人员：服务器管理员／运维人员

方式组成与适用范围本次验证状态
本机Python虚拟环境SQLite、私有原件目录、127.0.0.1监听；适合演练、验收与单机测试，不作为公网正式服务。Linux真实进程和HTTP、完整备份／空目录恢复已测试。
Docker Compose服务器PostgreSQL、迁移任务、应用、ClamAV、Caddy；对外HTTPS。交付编排和管理命令；本环境无Docker，未执行镜像构建或容器上线。
Linux原生systemd服务器已有PostgreSQL与ClamAV，Python虚拟环境，systemd托管；Caddy或既有nginx提供HTTPS。交付服务／网关生成器与维护命令；未实际执行systemd、PostgreSQL或HTTPS。
受控离线依赖安装预先下载匹配目标系统和Python版本的wheel文件，再用--wheelhouse安装。路径已实现；本包不含wheel或预构建镜像，未离线安装实测。
本版本为发布候选版，不把交付配置视为生产验收结果。请先完成文末的上线检查，再开放真实学生入口。服务器系统账号、域名、证书与资源由学校运维提供。

2. 解压、进入目录与配置文件

适用人员：服务器管理员／运维人员

把源码ZIP解压到一个固定目录，目录中应直接看到 manage.py、app、compose.yaml 等内容。下文命令均在这个目录执行。Linux原生服务器建议使用 /opt/bnu-evaluation，避免路径含空格或中文。

  1. Windows：打开解压后的文件夹，在地址栏输入 powershell 并按Enter，或在该文件夹打开终端。已安装Python时，也可双击“管理工具.cmd”。
  2. Linux／macOS：打开终端，执行 cd 后跟实际解压目录。路径含空格时用引号括起。
  3. 执行 python --version（必要时用python3）。建议使用Python3.13；当前实测3.13.5。脚本支持3.11及以上，但未逐一验证所有版本。
文件／目录作用是否随源码交付
.env系统密钥、入口、数据库与初始管理员配置。生成时拒绝覆盖旧文件。否，首次配置时本地生成。
.env.migration原生PostgreSQL迁移账号连接串。否，仅native方式生成。
.deployment.json本地记录部署方式；不能用它替换真实环境配置。否，配置时生成。
var/本机／原生数据目录：数据库或原件。否。
.runtime/本机进程身份记录及日志。否。
docs/手册、图文教程、核查与维护文档。是。
agent/外部Agent skill与客户端。是，不含令牌。
程序内部保留 clearledger 的Compose项目名、数据库名、技能目录名和 .zcp 格式标识，目的是保持已有数据卷、工程文件和接口兼容。这些技术标识不是界面产品名称，不要为改名随意更换旧数据卷。

4. 本机运行：Windows、Linux或macOS

适用人员：服务器管理员／运维人员

首次运行按顺序执行。Linux环境中命令可能是python3；Windows安装器提供py时也可使用py -3。

python manage.py configure --mode local
python manage.py install
python manage.py init-db
python manage.py start
python manage.py status
  1. install在当前目录创建.venv并安装requirements.txt固定依赖。无需先手工激活虚拟环境，管理脚本会调用正确的解释器。首次安装需要可用软件源或离线wheel目录。
  2. 打开浏览器，输入配置显示的地址，默认 http://localhost:8000。只在本机访问，不把localhost发给学生当作服务器地址。
  3. 用文本编辑器在本机打开.env。管理员登录名为admin；初始密码取BOOTSTRAP_ADMIN_PASSWORD，独立路径取ADMIN_PATH。管理网址为PUBLIC_ORIGIN与ADMIN_PATH连接起来。
  4. 首次登录修改密码，先建学院，再建教师，再由教师建学生名册。演练应使用演示资料，不导入正式密码表。
  5. 使用结束执行stop。下次只执行start，不再运行configure。移动安装目录后应重新创建虚拟环境，并核对DATA_DIR、数据库路径和管理记录，不直接复制旧.venv。
python manage.py stop
# 下次继续
python manage.py start
本机模式使用SQLite并不要求生产扫描器和TOTP，它仅是验证路径。不能把监听改为0.0.0.0并关闭安全限制后作为正式校园系统。更换端口应在首次配置时使用 --port，例如 --port 8010。

5. Docker Compose服务器部署

适用人员：服务器管理员／运维人员

前提：目标服务器已有Docker Engine与Compose插件，实际域名解析到该服务器，80／443端口按学校网络要求可访问；允许拉取镜像、安装依赖和更新病毒库。数据库与应用内部端口不对外发布。

python manage.py configure --mode docker --domain 你的实际域名
python manage.py install
python manage.py init-db
python manage.py start
python manage.py status
python manage.py health
  1. 把命令中的“你的实际域名”替换为分配给本系统的域名，只填域名，不加https://、路径或端口。不要直接复制中文占位文字。
  2. 保存.env的离线加密备份。将ADMIN_TOTP_SECRET以手工密钥方式加入学校批准的认证器：SHA1、6位、30秒。保证服务器和手机时间同步。
  3. install执行Compose配置校验和镜像构建；init-db启动数据库并运行迁移；start等待数据库、扫描器及迁移任务满足条件后启动应用和网关。
  4. 首次病毒库更新可能较慢。执行logs查看scanner、migrate、app、gateway；未完成扫描健康检查时不能关闭生产扫描强行上线。
  5. 通过实际HTTPS域名进入管理员独立入口，验证初次改密、动态口令、普通登录与文件上传。执行health只验证接口响应，不能替代这些业务与安全验收。
docker compose ps -a
docker compose logs --tail=100 database migrate scanner app gateway
# 暂停对外服务，但保留数据库和数据卷
python manage.py stop
严禁使用 docker compose down -v 作为普通停止、升级或排障操作。该命令会删除受管数据卷。镜像构建和实际容器恢复本次未在当前环境执行。

6. Linux原生部署：准备数据库与服务

适用人员：服务器管理员／运维人员

这条路径不需要Docker，但需要学校运维先安装Python及venv支持、PostgreSQL客户端和服务器、ClamAV服务，以及Caddy或nginx。以下步骤针对已有Linux基础设施，不自动更改系统软件源或服务安全策略。

  1. 建立专用无交互登录系统用户 bnu-evaluation，并将源码放在 /opt/bnu-evaluation。代码可由root维护，业务用户仅需读取代码并写入var目录。
  2. 在PostgreSQL中准备独立数据库，例如clearledger。迁移账号例如zc_migrator，负责该数据库的建表；运行账号固定为zc_app，不使用超级用户账号运行应用。
  3. 分别设置强随机数据库密码。先创建角色及空数据库，再通过本系统init-db授予zc_app最小运行表权限。不要把数据库密码放进shell历史或聊天。
  4. ClamAV监听127.0.0.1:3310，仅本机应用可连接，初始化并更新病毒库。参考deploy/clamd.conf，将其中TCPAddr改为127.0.0.1；其扫描上限要能接收允许的反馈附件。
# 在已获授权的PostgreSQL管理会话中执行结构创建；密码由交互命令输入
CREATE ROLE zc_migrator LOGIN;
CREATE ROLE zc_app LOGIN;
\password zc_migrator
\password zc_app
CREATE DATABASE clearledger OWNER zc_migrator;
上述数据库结构示例仅用于新系统。已有数据库不可重复建库或重置账号密码后不更新配置。使用学校既有数据库时，由数据库管理员落实等价权限与网络隔离。

7. Linux原生部署：配置、初始化与启动

适用人员：服务器管理员／运维人员

cd /opt/bnu-evaluation
python3 manage.py configure --mode native --domain 你的实际域名
# 按隐藏输入提示填写两条连接串，不要把密码作为命令参数：
# postgresql+psycopg://zc_app:已编码密码@数据库主机:5432/clearledger
# postgresql+psycopg://zc_migrator:已编码密码@数据库主机:5432/clearledger
python3 manage.py install
python3 manage.py init-db
python3 manage.py native-files

密码含@、:、/等URL保留字符时需要正确URL编码。使用不同的运行与迁移账号；.env保存运行配置，.env.migration保存迁移配置。按学校要求限制数据库来源地址并配置TLS。

# 在root或相应sudo权限下执行；目录与用户应已存在
sudo chown -R bnu-evaluation:bnu-evaluation /opt/bnu-evaluation/var
sudo chmod 700 /opt/bnu-evaluation/var
sudo chmod 600 /opt/bnu-evaluation/.env /opt/bnu-evaluation/.env.migration
sudo cp deploy/generated/bnu-evaluation.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable bnu-evaluation
sudo systemctl start bnu-evaluation
sudo systemctl status bnu-evaluation --no-pager
  1. systemd通过EnvironmentFile读取root控制的配置，再以专用业务用户启动程序。应用不需要能够直接读取root的.env文件。
  2. 原生应用仅监听127.0.0.1:8000，systemd自动重启失败进程。服务允许写var，不允许任意写系统目录。
  3. 在deploy/generated中选择一种网关模板：Caddyfile或nginx.conf。不要让二者争用同一端口。Caddy模板使用实际域名；nginx模板必须替换为学校现有证书路径。
  4. 校验并加载学校网关配置，确认HTTPS与转发头后执行 python3 manage.py health。start／stop／restart在native方式调用systemctl，因此需要相应系统权限。
单元文件和网关模板已生成并有结构测试，但并不代表目标主机已有服务用户、证书、扫描器或数据库。这些先决条件必须由运维完成，不能只复制.service文件就认定部署结束。

8. 不使用公网软件源的安装方式

适用人员：服务器管理员／运维人员

管理脚本支持本机与原生部署的wheel目录安装。应在与目标操作系统、处理器和Python版本匹配的环境中准备依赖，包含全部间接依赖；Windows的wheel不能直接当作Linux的wheel使用。

# 在匹配平台的联网准备机上，从已审核的软件源准备依赖
python -m pip download --only-binary=:all: -r requirements.txt -d wheelhouse
# 将源码和wheelhouse按学校规定传入目标机后
python manage.py install --wheelhouse /wheelhouse实际路径

Docker离线部署需要预先准备并审查依赖镜像和应用镜像，再通过学校镜像仓库或镜像传输流程装载。本交付不包含这些二进制镜像，也不声称已经完成断网镜像构建。

9. 完整系统备份

适用人员：服务器管理员／运维人员

备份前通知用户暂停操作，先确认最近业务数据已保存。每次使用一个不存在的新目录；脚本拒绝覆盖同名旧备份。

python manage.py backup /受控备份路径/2026-09-22-第一次
# 按提示输入“确认”
python manage.py verify-backup /受控备份路径/2026-09-22-第一次/system-backup.zip
部署方式备份内容运行状态处理
本机／原生system-backup.zip：数据库、原始对象、.env，原生另含迁移配置；manifest记录成员大小及SHA256。暂停应用写入后备份；原先运行时恢复运行，原先未运行则不擅自启动。
Dockerdatabase.dump、objects.tar、environment.secret、SHA256SUMS组成目录；verify-backup直接传这个目录。暂停app，使用pg_dump与原始卷配套备份；完成后只恢复原先运行的app。
# Docker方式校验整个备份目录
python manage.py verify-backup /受控备份路径/2026-09-22-第一次
完整系统备份含真实学生数据及APP_SECRET、数据库口令等密钥，敏感程度高于班级.zcp。必须使用学校批准的加密及离线保管方式。不要只备份数据库，不要把备份留在对外可下载目录。

10. 在空目录恢复本机备份

适用人员：服务器管理员／运维人员

  1. 不要在正在使用的系统目录执行恢复。先解压一份相同版本源码到新目录，里面不得已有.env或业务var数据。
  2. 进入新目录，执行restore指向已经校验的system-backup.zip。按提示输入“恢复到空目录”。
  3. 恢复会保留原APP_SECRET和账号密码，并将本机数据路径调整为新目录；不会自动启动。
  4. 安装依赖，运行verify检查原件与审计；停止旧本机实例后再启动恢复的实例，避免两者争用端口。
  5. 核对账号、反馈附件、业务工程和公示结果后记录恢复时间。旧系统不要立即删除。
cd /新的空白源码目录
python manage.py restore /备份目录/system-backup.zip
python manage.py install
python manage.py verify
python manage.py start
本机恢复仅接受local备份，拒绝在现有系统上覆盖恢复，也不会将PostgreSQL备份伪装成SQLite。此次已在隔离目录验证账号密码、资源引用与数据恢复。

11. 在隔离环境恢复Docker备份

适用人员：服务器管理员／运维人员

仅在新的隔离服务器或独立部署环境执行。Compose项目名相同，在同一Docker主机上直接运行可能引用旧卷；不能把“换了代码目录”误当作“空数据库”。

  1. 将源码解压到隔离环境。先校验备份目录，确认所有成员哈希、tar路径及原件内容正确。
  2. 将备份environment.secret复制为新目录的.env，不运行configure重新生成密钥。按文件权限要求保管。
  3. 目标数据库和原件卷必须为空。deploy/restore.sh会检查是否已有业务表或原件，非空就拒绝；它不会替您删除旧卷。
  4. 明确确认空环境后执行恢复。恢复数据库、原件、迁移／权限校验，等待扫描服务健康，再执行完整性verify。
  5. 脚本不自动开放gateway。人工验证工程、快照和账号后，再启动网关，完成域名和证书切换。
python3 manage.py verify-backup /备份目录
cp /备份目录/environment.secret .env
chmod 600 .env
CONFIRM_EMPTY_RESTORE=YES sh deploy/restore.sh /备份目录
# 人工核验业务后才执行
docker compose up -d gateway
实际PostgreSQL／Docker灾备恢复本次未运行。哈希只能证明与备份清单一致，不能替代备份来源信任和恢复演练。
返回目录

12. 在隔离环境恢复原生PostgreSQL备份

适用人员：服务器管理员／运维人员

native备份使用system-backup.zip，内含database.dump、environment.secret、migration.secret和objects。交互菜单的自动恢复入口仅用于本机SQLite；原生数据库恢复由有数据库权限的运维按以下步骤执行，不会在脚本中自动选择或清空数据库。

  1. 在隔离机器校验ZIP，核对来源；使用受控解压工具解到空目录。不要解压来自不可信来源的未校验压缩包。
  2. 准备新的空PostgreSQL数据库和迁移／运行账号。使用pg_restore --no-owner --exit-on-error，将database.dump恢复到明确选定的新数据库；不要使用--clean对正在运行的业务库删除对象。
  3. 恢复原environment.secret中的APP_SECRET、ADMIN_PATH及TOTP配置，保留原密码验证与签名所需信息；只把DATABASE_URL和DATA_DIR调整为隔离目标。migration.secret改为对应新迁移连接串并保存为.env.migration。
  4. 将objects目录恢复到新的DATA_DIR下，设置业务用户权限；重新安装对应版本依赖，运行init-db核验模式与运行权限，再执行verify。
  5. 安装并启动扫描器、systemd与网关。在人工核对全部业务记录后才接入正式流量。
这是交付的人工恢复操作规程，不是本次已经跑通的PostgreSQL自动恢复功能。恢复数据库时可能执行备份中已有对象定义，应只使用获授权可信备份；未经验证不开放业务入口。
返回目录

13. 从上一版本更新与回滚

适用人员：服务器管理员／运维人员

本次重构沿用数据库模式v1，保留盖章字段，新增可空的“向学生说明”字段，不改写旧标注历史。旧程序不一定认识新字段，不能仅替换旧代码继续读写新数据。先备份，在隔离环境演练，再安排停机升级。

  1. 先完成并校验全系统备份，记录正在使用的代码版本、Python版本和镜像摘要。
  2. 停止应用，保留原.env、.env.migration（如有）、var或Docker数据卷。替换代码时不能把源码包中的空目录当成业务数据覆盖。
  3. 安装本版固定依赖或重新构建镜像，运行init-db核验数据库与权限。使用原配置启动，执行verify及关键业务验证。
  4. 原生方式根据安装路径重新生成并核对systemd／网关文件；本机方式使用管理脚本启动后的新进程记录。不要拿其他进程PID填入管理文件。
  5. 需要回滚时停止服务，在隔离环境恢复与旧代码对应的备份并验证。仅替换旧代码不一定能读取新版本已保存的所有字段。
旧.zcp中的历史名字属于来源记录，字节不应仅为改系统名称而篡改。界面、文档、导出标题和交付名称已更名；旧档案真实性与可追溯性优先于抹去历史标识。
本轮验证了70人合成工程的导出、重新导入与计算一致性，没有重新评审真实学生资料。此项不表示整个生产数据库、所有旧第三方插件或反向降级已经验收。已有实例始终保留APP_SECRET、.env和数据卷。

rc4保留数据库表、工程格式、Compose卷和clearledger技术名称；新增的标注说明在JSON版本中保存，旧记录缺省为空。仍应先停止写入、备份并校验，再替换代码。不要用旧程序打开rc4新数据做直接回滚，回滚要恢复匹配版本的备份。

14. 常用维护命令与故障处理

适用人员：服务器管理员／运维人员

python manage.py check
python manage.py status
python manage.py logs --lines 200
python manage.py verify
python manage.py cleanup-sessions
python manage.py recover-admin
提示／故障处理
配置文件已存在不要重新生成。已有APP_SECRET与审计、历史验证有关；通过维护流程修改实际配置。
端口被占用查看实际进程／服务与配置。脚本不会为启动应用而杀死未知进程。
无法确认进程身份检查.runtime记录、日志和操作系统进程；不要手工填写其他PID或删除正在使用的数据。
备份结束后未能重启备份文件保留；先查看logs和端口。验证原因后启动，不把失败备份目录覆盖重用。
原件或审计校验失败停止向外分发受影响结果，保留日志，核对同一密钥与资源备份，交运维追查。不要直接重算签名掩盖问题。
管理员无法登录核对独立网址、初改密码、动态口令和时间。主机授权运维可recover-admin恢复同一个管理员。
扫描器异常恢复病毒库／服务和网络；正式模式异常应拒绝上传，不关闭扫描放行。
容量不足查看数据库、对象目录、备份磁盘与进程内存，先扩容／归档；不能删除已引用原件腾空间。

18. 截屏、表格回填与浏览器验收

正式服务提供HTTPS；反向代理不要移除应用的 Permissions-Policy: display-capture=(self) 或阻断同源截图能力。CSP仅对本地预览允许blob媒体，不放开任意外部脚本。需要用户点击才请求共享，不预授予或隐藏权限。

截图流在获取一帧后立即停止；浏览器／操作系统选择器无法被本机自动测试完整替代。应分别验收授权、拒绝、取消、窗口切换、裁剪、粘贴、屏幕缩放、无安全上下文和手机回退。
